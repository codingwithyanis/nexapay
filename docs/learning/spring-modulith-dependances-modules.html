Spring Modulith : comprendre les dépendances entre modules

Un monolithe n'est pas l'absence de frontières. C'est une seule application dans laquelle on choisit soigneusement qui peut connaître qui — puis on le vérifie à chaque build.

1. Quel problème cela résout-il ?

Le couplage invisible d'un monolithe qui grandit.

Dans une application compilée en un seul bloc, Java permet naturellement à Payment d'importer une classe privée de Merchant, puis à Merchant d'appeler Payment. L'application démarre encore ; mais une modification locale devient risquée, les responsabilités se mélangent et une extraction future coûte très cher.

Avant

Les packages sont une convention écrite dans un document. Elle est facile à oublier sous pression.

Avec Modulith

Les conventions deviennent des règles exécutables : les dépendances observées doivent correspondre aux dépendances autorisées.

Analogie. Un immeuble peut avoir une seule adresse, tout en ayant des appartements séparés. Sans portes, on traverse le salon du voisin pour aller travailler. Spring Modulith vérifie que les portes existent et que les passages autorisés sont explicites.

2. Quel est le modèle mental du mécanisme ?

Un graphe de contrats dans une seule JVM.

Chaque package direct sous le package de l'application est un module applicatif. Le package racine est son interface par défaut. Ses sous-packages sont internes. Une arête payment → merchant autorise Payment à utiliser le contrat exposé de Merchant, jamais son implémentation.

Idée clé. Ce n'est ni un appel HTTP, ni une base séparée, ni un microservice. Les modules restent dans le même processus ; la frontière est logique et testée.

3. Comment cela fonctionne-t-il sous le capot ?

Découvrir, modéliser, comparer, refuser.

  1. Découverte : ApplicationModules.of(NexaPayApplication.class) part de dev.nexapay et détecte ses packages directs.
  2. Analyse : Spring Modulith utilise ArchUnit pour importer les classes compilées et leurs relations : signatures, imports, appels, injections Spring, héritages et annotations.
  3. Politique : @ApplicationModule et, au besoin, @NamedInterface disent ce qui est exposé et autorisé.
  4. Vérification : verify() compare le graphe réel à la politique et fait échouer le test en cas de violation.
private static final ApplicationModules MODULES =
    ApplicationModules.of(NexaPayApplication.class);

@Test
void verifiesModularStructure() {
    MODULES.verify();
}

Dans NexaPay, ce code est dans ModularityTests. La règle actuelle dit que Payment peut dépendre de Merchant ; les autres modules n'ont aucune dépendance métier autorisée.

4. Quel est son lifecycle ?

La frontière est surtout contrôlée au build.

Maven compile, Surefire lance JUnit, puis JUnit appelle verify(). Au runtime, le starter core peut fournir d'autres capacités Modulith si elles sont ajoutées ; mais la protection de structure n'intercepte pas chaque appel de méthode dans la JVM. Elle est d'abord une vérification statique reproductible.

6. Comment et pourquoi peut-il échouer ?

Il échoue lorsque le code contredit la frontière annoncée.

Import interne

Payment importe un repository de Merchant. Répare avec une façade ou un contrat plus étroit.

Dépendance absente

Payment appelle Fraud sans l'avoir déclaré. Supprime le besoin ou fais évoluer la règle après décision explicite.

Cycle

Deux modules se rappellent mutuellement. Inverse la dépendance, extrais un contrat ou publie un événement local.

Module invisible

L'application n'est pas au package racine. Place-la à dev.nexapay, comme NexaPay.

Piège. Laisser allowedDependencies à sa valeur par défaut ne restreint pas réellement le module. Une règle large peut donner une fausse impression de protection.

7. Quels sont ses coûts et ses trade-offs ?

De la friction maintenant, moins de dette plus tard.

Coûts

Il faut décider les contrats, maintenir les règles et accepter que le chemin direct soit parfois interdit. L'analyse ajoute aussi du temps au test.

Gains

Une dépendance devient visible dans le diff et bloquée en CI. Une extraction éventuelle part d'un code déjà moins emmêlé.

Évite deux extrêmes : aucun contrat, ou une façade pour chaque détail. Un bon contrat inter-module est petit, orienté besoin métier et stable. Une façade qui expose tout est un mur avec une porte de garage.

8. Quand dois-je l'utiliser / ne pas l'utiliser ?

Quand le monolithe est le bon déploiement, mais pas le bon prétexte au désordre.

Utilise-le

Application Spring Boot avec plusieurs domaines, durée de vie importante, équipe qui veut empêcher les accès directs aux données d'un autre domaine, ou extraction possible plus tard.

Ne le force pas

Petit service à une responsabilité, prototype jetable, bibliothèque sans Spring, ou système déjà découpé en services avec frontières de déploiement réelles.

Spring Modulith n'est pas une étape obligatoire avant les microservices. Il est précisément utile quand le monolithe reste le choix opérationnel le plus simple.

9. Comment l'observer et le debugger ?

Lis une violation comme le récit d'une dépendance.

# Le contrôle d'architecture seul
./mvnw -pl apps/nexapay-monolith test -Dtest=ModularityTests

# Le même filet que la CI
./mvnw --batch-mode --no-transfer-progress verify

# La règle Payment actuelle
sed -n '1,80p' apps/nexapay-monolith/src/main/java/dev/nexapay/payment/package-info.java

Lis la chaîne complète : module source → type utilisé → module cible → règle attendue. Pose ensuite la vraie question : « Payment a-t-il réellement besoin de ce détail de Merchant ? » Le message d'erreur est souvent une piste de conception, pas seulement un obstacle de build.

10. Puis-je l'expliquer, le dessiner, l'implémenter, le casser et le réparer ?

Oui : fais-en un mini-laboratoire.

Implémenter

/** Payment peut utiliser Merchant. */
@ApplicationModule(
  allowedDependencies = {"merchant"}
)
package dev.nexapay.payment;

Casser volontairement

// Dans payment : à ne pas faire
import dev.nexapay.merchant.internal
    .MerchantRepository;

Le test doit alors échouer. Pour réparer, ne déplace pas seulement l'import : décide d'abord si Payment a besoin d'une façade Merchant, d'une interface nommée, d'un événement local, ou si le besoin appartient en réalité à Merchant.

Explication en une phrase. « Spring Modulith construit le graphe des dépendances entre nos packages métier et fait échouer le build lorsqu'une dépendance sort des contrats autorisés. »

11. Que se passe-t-il une couche plus bas ?

Du bytecode, des annotations de package et de l'analyse statique.

Une dépendance Java ne se limite pas à un import textuel. Elle peut vivre dans un champ, un paramètre, un type de retour, une annotation, une injection Spring ou un appel. Après compilation, ces références sont inscrites dans le bytecode. ArchUnit les lit sans démarrer l'application.

Les annotations de package-info.java sont elles aussi compilées. Spring Modulith les consulte, associe les classes à leurs modules, puis compare les dépendances observées aux dépendances autorisées. Plus bas encore : Maven compile, Surefire lance le test, la CI répète l'opération. C'est puissant, mais cela ne remplace ni l'autorisation, ni les transactions, ni les tests métier.
